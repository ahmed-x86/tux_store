# Architecture

Tux Store is a **tiny executable plus a set of shared libraries**. The executable contains no application logic; every feature lives in a `libtux_*.so` that is loaded at start-up and talks to the others over one message bus.

```
                  ┌──────────────────────── tux-store (host) ────────────────────────┐
                  │  dlopen libtux_*.so · owns the Hub · hands the main thread to UI  │
                  └───────┬───────────────────────────────────────────────┬───────────┘
                          │ publish / deliver (JSON over a C ABI)          │
   ┌────────────────┬─────┴───────────┬────────────────────┬───────────────┴──────┐
   │ libtux_ui.so   │ libtux_search.so│ libtux_thumbnail.so│  libtux_install.so   │
   │ Slint window   │ catalog, search,│ icons, covers,     │  pkexec + pacman,    │
   │ + UI state     │ details, lists  │ cache, network     │  live progress       │
   └────────────────┴─────────────────┴────────────────────┴──────────────────────┘
        every module also links the rlibs  tux-abi (types, ABI)  and  tux-pacman (logic)
```

## Why shared libraries?

- Each concern is built, tested and replaced on its own.
- The host stays a few hundred lines; a bug in a module cannot take the process down because every ABI entry point is wrapped in `catch_unwind` (`panic = "unwind"` is therefore mandatory in the release profile).
- The ABI is plain C + JSON, so modules need not be built by the same compiler version.

## The host (`tux-store`)

1. Chooses the module directory: `$TUX_MODULE_DIR`, the executable's directory, then `<exe>/../lib/tux-store`.
2. `dlopen`s every `libtux_*.so` there (sorted by name), checks `tux_module_abi_version()` and calls `tux_module_create(&HostApi)`.
3. Finds the module whose `tux_module_main_loop()` is 1 (the UI) and calls its `tux_module_run()` on the main thread. It blocks until the window closes.
4. Marks every module not-alive (so no more messages are delivered), then destroys them in reverse order.

Libraries are **never `dlclose`d**: Slint/winit leave thread-local destructors and global state that must outlive unloading.

### C ABI (exported by every module — generated by `export_module!`)

```
tux_module_abi_version() -> u32
tux_module_name()        -> const char*
tux_module_main_loop()   -> u32                    // 1 only for the UI
tux_module_create(const HostApi*) -> void*
tux_module_message(void*, const u8*, usize)        // one JSON-encoded Message
tux_module_run(void*)                              // main thread, UI only
tux_module_destroy(void*)
```

`HostApi` (host → module) carries `publish(ctx, bytes, len)` and `log(ctx, level, target, msg)`.

## Threading model

| Thread | Does |
|---|---|
| main | host `main`, then the Slint event loop (inside `libtux_ui.so`) |
| any (publisher's) | `Module::on_message` — must return quickly |
| per-request workers | `tux-search` spawns one short thread per request; newest search wins via a generation counter |
| `thumb-local` + 8 `thumb-net-*` | icon stages (see [ICON_FETCHER.md](ICON_FETCHER.md)) |
| install thread + 2 pumps | one transaction at a time; stdout/stderr readers |

## The Rust ↔ Slint boundary

The UI state is a single `State` value in a `thread_local!` on the UI thread.

- **Slint → Rust:** callbacks call `with_state(|st| st.method(..))`.
- **Bus → Rust:** `UiModule::on_message` calls `state::dispatch(msg)`, which uses `slint::invoke_from_event_loop` to hop onto the UI thread and then runs `State::handle(msg)`.
- **Rust → Slint:** list data lives in `Rc<VecModel<_>>` held by `State` and bound once with `State::bind`; scalar state uses the generated `ui.set_*` setters.

Slint structs are plain values; the UI follows read-modify-write for them (`get_current_install()` → mutate → `set_current_install()`).

## Typical flows

**Open a package** — UI `DetailsRequested` → search runs `pacman -Sp` + `-Si` → `DetailsReady` → UI renders; the installer overhears it and caches the package sizes.

**Install** — UI `InstallRequested` → installer emits `OperationStarted`, `OperationOutput…`, `OperationProgress…`, `OperationFinished` → UI updates bar/console and flips the *installed* flag in every list; search drops its caches.

**Screenshots** — UI `ScreenshotsRequested` when a package page opens → thumbnail uses local files, the cache, or downloads from Flathub → `ScreenshotsReady{images}` (repeated as pictures arrive) → the slider's model is replaced. See [SCREENSHOTS.md](SCREENSHOTS.md).

**Icon** — UI `IconRequested` (once per package) → thumbnail resolves it offline or with one HTTP request → `IconReady{path}` → UI patches every visible card.

## Where things are found at runtime

| What | Looked up in order |
|---|---|
| modules | `$TUX_MODULE_DIR`, the exe's directory, `<exe>/../lib/tux-store` |
| data | `$TUX_DATA_DIR`, `<exe>/../share/tux-store`, `<exe>/../../data`, `<exe>/data`, `./data` |
| cache / config | `~/.cache/tux-store`, `~/.config/tux-store` (honours `XDG_*`) |

The first data candidate that contains `categories.json` wins. This is what lets the portable tarball run in place and `cargo build` output run from the source tree.

## Adding a module

1. Create `crates/tux-foo` with `crate-type = ["cdylib"]` and a dependency on `tux-abi`.
2. `impl Module for Foo { fn create(bus) …; fn on_message(&self, msg) … }`
3. Put `tux_abi::export_module!(Foo, "foo");` in the crate root (`lib.rs`).
4. Add the crate to the workspace `members`. The host picks up `libtux_foo.so` by file name.
5. New message kinds go into `tux_abi::message::Message` (see [MESSAGE_BUS.md](MESSAGE_BUS.md)).
